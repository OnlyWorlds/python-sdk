# Convention profile: map space


**What it is.** How a reader turns the standard's four map-space types into geometry: a Map's frame, a Zone's outline from its Markers, a Pin's point. The standard already says every part of it in its field descriptions (coordinates from the bottom left, `order` for the sequence, `shape` for how markers join, `depth` for z); two readers (the Unity package's C#, the Shell's `model.js`) carry the same rules with no page to replay against, and an engine would be the third copy. This page states the rules once, with a fixture. The geometry adds nothing to the world: no field, no mark, nothing stored. Two marks are a layout tool's, and rules 8 to 10 say how every tool reads them: `x_layout` on a Map (the Map is a drawing of its elements, and how it was drawn) and `x_hand` on a Pin (placed by hand); a second, small reading answers them for one Map. Rule 11 says what a tool that picks a Map, or measures or places by one, does with a layout map, and rule 12 when a writer marks one. Rule 13 says where a child Map lies on its parent (`x_parent_frame` on the child), and rule 14 how a point on the child is carried up to its parent and on; a third small reading answers both for one Map. Looks, cameras, lifts, doors, walls and rooms are a drawing tool's and are not here.

**The reading.** `mapSpace(elements)`, one reader in the SDK and the Python package (`map_space`), from the fixture beside this page. `elements` are the elements as the reader is served them (the folder's rows, or the API's), so visibility is already applied: a hidden Zone and its Markers are not in a member's or a visitor's input, and this page never brings them back. The answer is `{maps, zones, pins, out}`, in that order, every key always present. Everything is keyed by id and holds integers in the Map's pixels; a tool converts to its own units from the scale this page reports.

**The rules.**
1. **Coordinates.** `x` and `y` count from the bottom left of the Map, in the Map's pixels; `z` is in the same pixels, upward, and the Map's `depth` is the z extent. `z` is a point's elevation, never a height: a Marker at z 300 sits 300 pixels up, and a zone's height, where a tool wants one, is the tool's own key (the first folder read against this page had written a room's height into every Marker's z, and its reader read it back as wall height; both moved the same day). All are whole numbers as the standard says. A missing `x` or `y` on a Marker or Pin, or one that is not a whole number, leaves that row out, counted `no_point`; a `z` that is missing or not a whole number reads as 0. A reader holds a whole number within the range it holds exactly and reads a value past it as not whole: a value a parse had to round is not whole, so a reader whose JSON numbers are doubles holds whole numbers to 2^53 and reads past it as not whole; the fixture keeps every number within 2^53, so every reader answers alike. A `z` past the Map's `depth` is kept as written and never clipped: the reader reports, it does not fix (the Map entry carries `z_max`, the largest z among its points, beside `depth`, so a tool sees the overrun).
2. **Maps.** One entry per Map the reader is served: `{id, width, height, depth, z_max, scale, location, parent_map}`. A Map without `width` or `height` reports the extent of its own placed Markers and Pins (the largest x and y among those with a whole x and y that name the Map; a dangling or unplaced point measures nothing) in that slot, with `extent: "points"` beside it, so a drawing tool knows the frame was measured, not authored. A `width` or `height` that is a whole number is answered as that number, 0 and a number under 0 included; any other value, or none, is measured. A slot measured on a Map with no placed point of its own answers null, still with `extent: "points"`. A `depth` that is a whole number is answered as that number too; any other value, or none, reads null and is never measured.
3. **Scale.** `scale` is metres per pixel: the Map's `x_metres_per_pixel` when it carries one (a decimal; the convention this page reads, as the lens profile read `x_lens`, until a scale field reaches the standard by motion), else `null`; a number passed through as given, with no byte guarantee across languages (a `1.0` prints as `1` in one and `1.0` in another; its decimals never had one). The World's `length_unit` is not a map scale and this page does not read it as one. A tool with no scale draws in pixels.
4. **A Zone's outline.** The Markers whose `zone` names the Zone and whose `map` names one Map, in `order` ascending, ties and missing `order` by id in code point order (an `order` that is not a whole number reads as missing). Id order is the one answer a folder and a server give alike; it is the making order only when ids are uuidv7, and this page does not claim it otherwise; one outline per Map the Zone has placed Markers on, as `{zone, map, shape, points}` with each point `[x, y, z]`. A repeated point is kept as written. `shape` is the Zone's own `shape` when it is `polygon` or `line`; empty, absent or any other value reads as `polygon`, as the field's description says. A Zone with no placed Marker has no outline and is counted `no_markers`, each of its unplaced Markers under its own reason; a Marker whose `zone` or `map` is not served is counted `dangling`.
5. **A Pin's point.** One entry per Pin whose `map` is served: `{pin, map, element_type, element_id, x, y, z}`. The element is the generic link as the wire serves it and a folder writes it, `element_type` and `element_id`; a Pin with neither, or with only one of the two, is still a point (a place with a name and nothing it stands for), with both null. A Pin whose element is not served keeps its ids: the reader may know the id without the row.
6. **Out.** `out` counts what the reading left aside by reason: `no_point`, `no_markers`, `dangling`, `no_map`. A reason with nothing counted is absent.
7. **A stable order.** `maps`, `zones` and `pins` by id in code point order (outlines by zone id, then map id); the same input gives the same answer, byte for byte.
8. **A layout map.** A Map whose `x_layout` is an object with a non-empty string `method` is a layout map: its Pins are a drawing of its elements, laid out by that method, or by hand when `method` is `"hand"` (a board). The mark is this key alone, never the supertype or a missing picture; `x_layout` absent, null, not an object, or without a non-empty string `method` is no layout. One key is the mark and the recipe, as `x_lens` is for a lens. The method word `hand` is this page's; `by-kind`, `around` and `by-links-3d` are the default layouts page's (`profiles/layout.md`); any other method string is the tool's own until that method has a page, or a section on one (`trail-by-place` is the first in use), and a reader that does not know one reads the Map as a layout map all the same. A method word is read whole: `by-kind-2` is not `by-kind`. The stored Pins are the layout: a tool that draws a stored Pin draws it where it stands. No tool draws an element the Map has no Pin for as though the Map placed it, or another picture as this Map; what any tool draws beside the stored Pins without saving is the tool's. Reading or drawing a layout map adds, changes or removes none of its Pins or Markers and leaves its frame and its `x_layout` as they are: laying it out again, or placing on it the elements it does not place, is a write like any other and never a side effect of reading or drawing the Map; a write a tool makes by itself as a Map is opened or drawn is such a side effect, whatever setting ordered it. A tool that tells how many, or which, elements the method would place that the Map does not place uses the reading on the method's page where there is one (`unplaced` on the default layouts page).
9. **The ground.** `x_layout.settings.ground`, `{map, width, height}`, names the Map the layout stands on: `map` is its element id in the same world. A tool that draws a ground draws that Map's picture under the Pins. When the ground Map is served, its own `width` and `height` win over the recipe's; when it is not, there is no ground, and the layout is drawn on nothing. A ground with no `map` is no ground, and so is a ground whose `map` is the layout Map itself.
10. **A hand Pin.** On a layout map, a Pin with `x_hand: true` was placed by hand: a method that lays the map out again keeps it where it is and lays the rest around it. Only `true` is the mark; absent, `false` or any other value (`"true"`, `1`) reads as placed by the method. On a board every Pin is placed by hand, marked or not: nothing lays a board out again. A writer that places or moves a Pin by hand on a layout map sets the mark (a drag, a place at a tap); on a Map that is not a layout map it writes nothing, since every Pin there is placed by hand already. A method never sets it. Removing it hands the Pin back to the method's next lay-out. A writer that gives a Map with Pins a method other than `hand` marks every Pin on it `x_hand: true` first, then writes `x_layout`, or refuses: an act cut short leaves marks a plain map ignores, never unmarked Pins under a method. The order binds a Map that held Pins before the method, not a Map written new in one act with its method (a folder writer may write its Pins before its `x_layout`). On a Pin of a Map that is not a layout map, `x_hand` means nothing: a reader ignores it, and a writer need not clear it, so a Map whose `x_layout` is removed reads plain with its marks still on.
11. **Picking a Map.** Which Map stands for the world's space when a world has several stays the tool's (below). One thing is ruled: a layout map is no candidate. A tool that picks a Map for the world's space, by whatever rule of its own (no `parent_map`, the most Pins, a picture, a name, the order read), reads each Map's layout first (rule 8) and leaves out every Map that is a layout map. And a Pin on a layout map says where its element stands in that drawing, drawn over a ground or not (rule 9), and a Marker there where its Zone's outline runs in it, never where either is in the world: a tool that measures between elements or places an element in the world reads no Pin and no Marker of a layout map. A world whose every Map is a layout map has no Map for its space, and a tool says so; a tool that shows layout maps still opens one as what it is. The map-space reading and the layout reading answer a layout map as before, its Pins and its Markers with it; this rule is on the tool that picks or places from them.
12. **Who writes the mark.** The writer that knows what the Map is. A tool that lays Pins out by a method writes `x_layout` with that method; a tool that imports a surface its source holds as a board (cards placed by hand on no map of a place) writes `{"method": "hand"}`; a tool that makes a Map a person names, for whatever they mean by it, writes nothing, and may offer the person a control that says "this is a board". The test is what the Map is, never the source's word for it: an importer that meets a board holding a map of a real place marks nothing, and that Map is a plain Map (a ground when a layout names it). A method that places every Pin where its element is in the world and names no ground makes a place, not a drawing, and writes no mark: the Map is the world's space, whatever placed its Pins, and nothing on the standard's side lays it out again (the tool keeps its own recipe in its own namespace).
13. **A child Map's parent frame.** A Map's `x_parent_frame`, its parent frame, is a list of four numbers `[x0, y0, x1, y1]`: two corners of a box in the pixels of the Map its `parent_map` names, counted as a Pin on that Map counts them, from its bottom left (rule 1). The child's own rectangle, from (0, 0) to (`width`, `height`), lies on that box, each axis by its own ratio: a box of another shape than the child's is a stretch, not a fault, with no threshold and no refusal, and neither axis takes the other's ratio. Nothing turns: the child's axes are the parent's, a plan drawn turned carries its turn inside its picture, and the key says no rotation and a reader reads none. The parent frame places and a scale measures: a reader reports both as the world holds them, takes no scale from a parent frame and no parent frame from a scale (rule 3), and reconciles neither with the other. The key is read only on a Map with a `parent_map` (a link as reading H reads one); on a Map with none, a key that is present and not null is not read, with the lint `no_parent`, whatever it holds. It is a parent frame when it is a list of exactly four numbers with x0 less than x1 and y0 less than y1, the four compared as 64-bit floats. A number here is a JSON number a reader holds as a finite 64-bit float: a string, a boolean, null, a list and an object are none, and so is a number too large for a 64-bit float. A value that is not a list of exactly four numbers (a list of another length, one that holds anything that is no number, or no list at all) is no parent frame, with the lint `not_four_numbers`, and its first four are never read; a box with x0 not less than x1, or y0 not less than y1 (mirrored, or with no width or no height), is no parent frame, with the lint `not_a_box`, and is never normalised. A key that is absent or null is no parent frame, with no lint. A Map with a `parent_map` and no parent frame has no place on its parent: a tool may still go into it by the Pin of its `location` on the parent, or by a layout file of its own, and that is a way in, not a place. A child whose `width` or `height` is not a whole number above 0 (by value, as reading K reads one) has its parent frame and no carry: the parent frame is reported, and no point is carried through it. The size a parent frame divides by is the written one, never the extent rule 2 measures from the child's points (that extent moves whenever a Pin is added, and every carried point with it); 0 and a size under 0, which rule 2 answers as written, divide by nothing or turn the box over.
14. **Carrying a point.** A point (x, y), two numbers whole or not, on a child with a parent frame and a carry is, on its parent, `x0 + ((x * (x1 - x0)) / width)` and `y0 + ((y * (y1 - y0)) / height)`, in 64-bit binary floating point: the point, the four numbers and the two sizes each read as a 64-bit float, and each step taken in the order the parentheses write, the difference, then the product, then the quotient, then the sum. Sixty-four bits alone is not the rule; the order is: the step per pixel taken first, the fraction taken first, a carry from the box's centre, and exact rationals rounded once each give another last bit on some points, and two readers that keep this order give the same bits. Nesting composes: a point on a plan framed on a town map framed on the land is carried by the plan's parent frame onto the town map, and that point, as the carry gave it, by the town map's parent frame onto the land, one level at a time up the `parent_map` chain, never through one product of the levels' ratios. At each Map the walk reaches, the first of these that holds ends it, served-ness before shape as in reading A: the Map has no `parent_map` (`top`); its `parent_map` names a Map the reader is not served (`dangling`); it names a Map the walk has already reached, the Map itself included (`cycle`), so no point is carried onto a Map twice; the Map has no parent frame (`no_frame`); or it has one and no carry (`no_carry`). A point outside the child's rectangle is carried as written and never clipped. `z` is not carried: a parent frame says nothing of `depth`. A reader that keeps a point in 32 bits carries it in 64 and rounds once, when it draws or stores it; that rounding is the reader's own and outside what the fixture compares. The small plates of the default layouts page's `by-links-3d` stand at a Map's `location` and read no parent frame: they are a drawing, not where a child lies, and this rule does not move them. Where a Zone has an outline on a child Map and on its parent (rule 4), no reading on this page joins the two outlines, or adds a point on the edge of the child's rectangle or of its parent frame. What a tool draws of the Zone inside the parent frame and past it, and whether it shows the parent's outline through the parent frame, is the tool's.

**The layout reading.** `layoutOf(map, maps, pins)`, one reader in the SDK and the Python package (`layout_of`), from the fixture's `layout_cases`. `map` is one Map, `maps` the Maps the reader is served, `pins` every Pin the caller holds, of any Map, as served; the reader itself keeps the Pins whose `map` names this Map's id, and reads a row as the map-space reading does (H: a row without a non-empty string id is no Pin, and a Map row without one is no Map, so the reading answers `{layout: null, ground: null, hand: []}` for it, whatever it carries; I: the last row served for an id wins). The answer is `{layout, ground, hand}`, in that order, every key always present:
- `layout`: the `method` string when the Map is a layout map (rule 8), else `null`. A method no page names answers itself.
- `ground`: when `layout` is not null, the id in `x_layout.settings.ground.map` when it names a served Map that is not this Map; else `null` (rule 9). The ground's size is not returned: the caller holds the served Map.
- `hand`: the ids of the Pins a new lay-out keeps where they are, by id in code point order (rule 7's order). On a board, every Pin of this Map; on any other layout map, the Pins whose `x_hand` is exactly `true`; on a Map that is not a layout map, `[]`, whatever its Pins carry (rule 10).

A Pin whose element the reader cannot see is still a Pin and is listed when it qualifies. A method's own `settings` are not returned or ruled here, the ground apart. The map-space reading is unchanged by rules 8 to 10: its answer carries no layout key.

**The frame reading.** `carryOf(map, point, maps)` (`carry_of` in Python), from the fixture's `frame_cases`. `map` is one Map, `point` is `[x, y]` on it (two finite numbers in its pixels from its bottom left, as a Pin's `x` and `y` or a tap gives them), and `maps` the Maps the reader is served; the reader reads a Map row as the map-space reading does (K: `type` exactly `map`; I: the last row served for an id wins; H: a link that is not a non-empty string is no link, and a Map row without a non-empty string id is no Map; a row that is no Map by K or H answers `{parent_frame: null, lint: null, points: [], stop: null}`, whatever it carries). The answer is `{parent_frame, lint, points, stop}`, in that order, every key always present:
- `parent_frame`: the Map's `x_parent_frame` as written when it is a parent frame (rule 13), else `null`; also on a Map whose parent is not served or closes a ring, which ends the walk and leaves the parent frame its own.
- `lint`: `no_parent`, `not_four_numbers` or `not_a_box` when this Map's own key is one (rule 13), else `null`. A Map further up the chain is read for its own lint by its own reading.
- `points`: each `{map, x, y}`, first the point on this Map as given, then the point on each Map it is carried to, in order up the chain (rule 14), each `x` and `y` the 64-bit float the carry gives.
- `stop`: why the last point in `points` is carried no further: `top`, `dangling`, `cycle`, `no_frame` or `no_carry` (rule 14).

The point on the parent is `points[1]` where there is one; the point on the top of the chain is the last when `stop` is `top`; a tool that wants one Map above reads the entry with that Map's id, and finds none when the walk stopped below it. `parent_frame` and `lint` are this Map's own and do not depend on `point`. The reading reports no scale and takes none from a parent frame, and it reads a layout map as any Map: rule 11 is on the tool that places from one. The map-space reading is unchanged by rules 13 and 14: its Map entries carry no parent frame.

**Readings ruled on the fixture** (2026-11-02): A, a Marker that is both dangling and without a point counts once, as `dangling` (served-ness before shape). B, a Marker without a whole `order` sorts after every ordered one, then by id (where the ids are uuidv7, as keel mints them, that is the order they were made in): a stated order outranks an unstated one. C, a Pin with one of its two keys reads both null. D, a `width` or `height` that is missing or not a whole number is measured from that Map's own Markers and Pins only, and with no placed one of them it is null. E, `scale` is set only when `x_metres_per_pixel` is a positive number, else null. F, `extent: "points"` appears only when a slot was measured. G, a `z` past `depth` is kept. H, a row without a non-empty string id is no element: ignored, never counted (an element is its id; what has none was never served); a link whose value is not a non-empty string is no link and is read as an absent one: an empty string, a list, a number, a boolean, an object, as an id that is empty is no id (a Pin left with one of its two element keys then reads both null, rule 5). I, two rows of one type with one id: the last row served wins, for every type (a reader holds one row per id). J, reading A reaches Pins: a Pin with neither a served map nor a point counts once, as `no_map`. K, `type` and `shape` are read case-exactly: `Map` is no Map and `Line` is a polygon, as the field's own sentence says lowercase. And a whole number is a JSON number with no fractional part, whatever its spelling: `2.0` reads as 2, `1.5` and `"2"` do not read; a reader in a language that keeps the spelling converts, never refuses, on the value.

**What stays the tool's**, said so nobody ports it as a rule: which Map stands for the world's space when a world has several, among those rule 11 leaves; a default scale when none is given (the C# takes 0.05); hull, area and room roles read from `role` or `x_` keys; doors as Objects with Pins, their widths and wall snaps; a lift factor on z; cameras and looks; how a layout method places where no page rules it, and its own `settings`; what a layout method does with a layout map's Markers; a way into a child Map that has no parent frame (the Pin of its `location` on the parent, a layout file beside the world), which is never a place; how a child's picture is drawn on its parent's, and what is drawn of a Zone outlined on both (rule 14). A reader that wants those builds them on this page's answer.
