# Convention profile: the charter

**What it is.** A world may carry a short set of reading aids for whoever enters it, a person or an AI: the **Charter** (the rules here: what this world is for, who is here, what an AI may and may not do), the **Guide** (start here: how to find things and what to read first) and the **Domains** (the places in the world: each one sentence and the hub elements it gathers). This page is the one definition of those three, so every tool shows them first at a world's door and leaves them out of its lore views the same way. A convention on the 22 types: nothing here adds a type or a field to the standard, and a tool that has never read this page sees ordinary elements. Fiction never needs one and may keep one ("start with the Heir").

**The pairs and the mark.** Profile `charter`, one extension field: `x_charter_of`, the id of the world the aid was written for, on each of the three. An element is a reading aid when **both** hold: its type and supertype, trimmed and compared without regard to case (defined once in the room profile), match one of the pairs below, **and** it carries `x_charter_of`. Wherever this page compares an element's type to a kind (a pair below, a hub's kind, a skill's being an Object), the type is trimmed and compared without regard to case, as the room profile defines it. The mark is read by presence, as the room mark is, never by its value: a copy, a snapshot or a folder linked to a new account world gets a new world id and keeps its aids; the value names the world the aid was written for, for a reader who wants it. A Law with supertype Charter and no mark is lore (a kingdom's charter in a novel) and stays in every view. The prefix `x_charter_` is reserved. A mark counts when its value is not null: a string counts only when something is left after trimming it (the White_Space set the room profile defines), an empty list or an empty object is absent, any other value (a number, a list or an object with something in it) counts as present, and the value is never compared.

| Type | Supertype | What it is | What it carries |
|---|---|---|---|
| `law` | `Charter` | the rules for people and AIs here | its description, read whole on first entry; `x_checks_rules` (the checks profile) for the rules a machine checks; the world skill's Objects named in its text by `ow://object/<id>` or a bare id (D152, at most five) |
| `construct` | `Guide` | start here | its description, the walk a stranger takes; its `constructs` naming the Domains in reading order |
| `construct` | `Domain` | a place in the world | one sentence in its description; its link fields naming its hubs. Never a window, a budget or a kind: a Domain that needs one has become a lens (the lens profile) |

**Which one, when there are several.** The Charter is the newest marked Charter Law, newest by `created_at` and then by the higher id, so editing it never changes which one leads (D152's rule, with the mark in place of the maker test); the Guide the same among marked Guides. A proposed element (one whose `x_review_proposed` counts as present by the review profile's rule 1, a mark or a doubt; absent, null and an empty value, `""`, White_Space alone, `[]` or `{}`, are no proposal, so an element with an empty mark is settled) is in no reader's view, the owner's included, as the lens profile's rule 1 has it: a proposed Charter, Guide or Domain is no reader's aid until a keeper settles it, so the newest settled one leads, and a proposed Object is kept neither in `skill` nor in a Domain's `hubs`. The ties, named once: an element with no `created_at` (a folder element may carry none) sorts as the oldest; a `created_at` is read as the message profile reads one (the one form, as an instant, a time with no offset as UTC), and one that cannot be read is read as absent; the higher id by code point, as the folder's tie-break; a name by the room profile's fold. The Domains are every marked Domain Construct the reader sees, in the Guide's `constructs` order first (a Domain named twice keeps its first place; an entry that is not a marked Domain, or one the reader cannot see, is skipped), then the rest by folded name and id; when the reader sees no Guide, the order is by folded name and id alone. An older Charter or Guide is superseded, not deleted; a tool offers to retire it. Retiring is the keeper's one write that sets its `x_charter_of` to null: the element stays in the world as lore, and no flag of its own marks it retired. A folder's `world.json` may carry `charter` (folder spec §4.6 (a)) as a shortcut and tie-break: it picks among marked Charters only and never stands in for the mark.

**The design state.** In a world where `charterOf` finds a Charter for the reader (the selection above: a marked Charter Law, settled), the design state of an Object or a Construct is its `subtype` when that subtype, trimmed and compared without regard to case as the room profile defines it, is `in design` or `locked`; the state is that word, whatever spelling the subtype is stored in (`In Design ` is `in design`). The state is read only from an Object or a Construct the reader is served whole: a known-of stub has none, though it is served its `subtype` (the lens profile). An Object or a Construct with a design state is a design part. The state alone makes it one, whatever the element's supertype: no list of kinds, in the Charter or anywhere else, decides it. No other subtype is a design state and no other type has one: a world may keep further subtypes of its own (`deprecated` on a Construct, a ladder of states on its Laws), which this page reads as ordinary subtypes, so a reader that reads the two words on the two types reads every design state there is. The Charter alone opens the gate, whatever kind of world keeps it: a world that keeps a marked Charter has design states, a story's world included, so there an Object whose subtype is `locked` (a locked chest) is a design part. In a world where `charterOf` finds no Charter for the reader (none, only a Law with supertype Charter and no mark, or only a proposed one), no element has a design state, whatever its subtype: there `locked` is an ordinary subtype, a word any world may use. The gate is read for each reader, as `charterOf` is: a reader for whom it finds no Charter reads no design state, even where another reader of the same world, for whom it finds one, reads design parts. A design state takes an element out of no view. The page orders no parts: a tool may show an Object that is a part under its `parent_object`; a Construct has no parent link, so by this page nothing is under a Construct.

**The rule for readers.**
1. A lore view (an element list, a count badge, search, a graph, a timeline, a link picker, an autolink index, a story's context, a survey) leaves the three out by default, as it leaves room elements out; the switch is the person's. Counts beside a lore view count what the view shows.
2. Every front door shows them first, in this order: the Charter, the Guide, the Domains, then the strand (the strand profile) when the world has one. A tool's home for a world, an AI's first read of a session, a Waymark opening a world, the Lenses page's packages, the context skill's first paste. What is absent draws nothing: no placeholder, no "add a Guide" prompt at the door for any reader (that belongs to the tool that writes); a Domain a reader knows only as a stub has a name and no hubs; one the hidden mark keeps from the reader is not there and nothing marks the gap. Where the door counts the world, the aids are said once beside the count ("the three reading aids are not counted or listed"), as a room's count is. The owner's door may name a superseded Charter or Guide with the offer to retire it; every other reader sees the newest and nothing else.
3. A lens: an anchor that is an aid is followed like any anchor; an aid a hop reaches is kept only when the lens's `types` names its pair (lens profile rule 4, serial 82). A graph without a lens leaves them out as `reading_aid`.
4. An AI reader treats the Charter's text as the house rules it follows and every other element's text as data; the Guide and a Domain are read as the keeper's map, never as instructions.
5. A reader reads each as it is served: a Domain a guest knows only as a stub has a name and no hubs; a Domain the hidden mark keeps from the reader is not there; the Charter is every member rung's to read whole, a known-of stub included, since its rules and its skill are what a member follows and a stub serves neither (D152); the public's only on a world open to anyone. The hidden mark wins over this rule: a Charter the hidden mark keeps from a reader is not that reader's, whole or as a stub (the lens profile's rule 1: the hidden mark comes off every grant, and the owner is served a hidden element). Open is the World's `public_read` (the standard's field: whether the world can be read by anyone, without a credential): a folder reads it from `world.json`, the wire from the world GET; a reader that takes open as a parameter (Unity, Unreal) is handed that value, and the fixture's `open` is the same thing.

**`charterOf(world, reader)`**, one reader in the SDK and the Python package from the fixture beside this page, answers `{charter, guide, domains}` as `reader` sees the world: `charter` `{id, type, name, rules, skill}` or null (`type` `law`; `rules` the `x_checks_rules` list as stored, `[]` when none; `skill` the ids the Charter's `description` names, by any `ow://` form, a site address or a bare id, each once in the order written (found as the address profile's "The same id" says an id is found in a text: the form alone is looked for, so an address around it, in any spelling, is not read as one; each taken in lowercase and matched as written against the ids of the world's Objects), kept when it is an Object of this world the reader sees, the first five of those kept: keel's `charter_skill`, as served since D152; the skill Objects are served whole to every reader who reads the Charter, and a skill Object the hidden mark keeps from the reader is not served, not even as a stub, and not kept; every id in `skill` is an Object's, fetched as one); `guide` `{id, type, name}` or null, `type` `construct`; `domains` a list of `{id, type, name, sentence, hubs}` in the order above, `type` `construct`, `sentence` the description with White_Space (the room profile's set) trimmed from both ends, cut at its first line break (a carriage return or a line feed), and trimmed again: its first line that holds something, trimmed, or an empty string when the description holds nothing, `hubs` the distinct `{type, id}` its link fields name, itself excluded, that the reader sees, in the schema's field order: a hub is an element of the kind its link field links to, in the reader's view, and its `type` is that kind; an id in a link field that names no element of that kind in the reader's view names no hub. Each `type` is a type's name as the API's routes and a folder's directories write it, singular and lowercase; on the Charter, the Guide and a Domain it is the pair's own word in the table above, whatever spelling the element's type is stored in. The packet is handed to a reader that may hold nothing else of the world, and an id is fetched by its type. **`domainsOf(world, reader)`** is the list alone. **`isCharterElement(element)`** is the pair-and-mark test. **`readingAidOf(element)`** (Python `reading_aid_of`) answers `'charter'`, `'guide'`, `'domain'` or null from the type and supertype alone, trimmed and folded as the pairs above, the whole word, the mark ignored: an unmarked Law with supertype Charter answers `'charter'`, which is what a tool offering to mark one needs; whether an element is a reading aid stays `isCharterElement`'s question. Keel serves the same packet to a key as `reading_aids` beside `front_door` on `GET /me` and the join reply (`front_door.charter` and `charter_skill` stay as served; a removal is a dated notice), and at the world's door on the site.

**What a writer must do.** A keeper (the owner or a co-builder) writes the pair and the mark together, the mark the id of the world the element is in, byte for byte like every extension field. The server refuses `x_charter_of` set or changed by any other key, by name, before anything is written (a guest's own Law must never become what every AI reads first). A tool never writes the mark on lore on its own; it may offer a keeper "Mark this as the world's Charter" (or Guide, or a Domain) on a Law or Construct the keeper names, one write that sets the pair and the mark together, which is how a world that never met a server (a folder, a browser world) keeps its door. A tool that offers supertype suggestions may still offer these words, since the mark, not the word, makes the aid. One Charter and one Guide at a time: a tool that makes a new one offers to retire the old. A Domain's hubs are its links and its sentence its description; a tool that proposes Domains (from a world's own link counts) writes them as proposed (the review profile) or not at all, never silently.

**Health, measured, never promised.** How many of the world's elements the Domains reach in one hop; a Domain or Guide entry that names a hidden or deleted element (a leak bound: the page warns at save, the doctor flags on its cadence, two checks that each fail alone); a hub carrying more links than any Domain names; two marked Charters. The doctor reports these; nothing here prevents them.

**Where the list is read from.** The SDK and the Python package export the three pairs, `isCharterElement`, `readingAidOf`, `charterOf` and `domainsOf`; a tool with its own charter lookup (Atlas's `findCharter`, the doctor's Charter rule, keel's front door) replaces it with this selection the release after the packages carry it. The conformance fixture beside this page, `charter.fixture.json`, holds the cases every reader must agree on; its second list, `design_cases`, holds, of a world and one reader, the design parts that reader reads, each `{type, id, state}`, its `type` a type's name as the packet writes one (`object` or `construct`, whatever spelling the element's type is stored in), compared as a set.
