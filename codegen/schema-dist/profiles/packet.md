# Extension profile: `x_packet_*`

**What it is.** A packet of work about a world: a list of elements with a reason each, made by a tool (a world doctor's findings), a person (an ask: "look at these four") or an AI (a proposal). The packet travels as JSON until it lands as an element; landed, it is a Relation with supertype `Work item` and the packet's fields ride on it, so every tool that follows a work item reads one shape: the parlor's list, Atlas's import by the id list, the doctor's output, a seat's proposal.

**Key names.** Profile `packet`, five fields: `x_packet_elements`, `x_packet_source`, `x_packet_producer`, and two optional, `x_packet_for` and `x_packet_from`. The grammar is `x_<profile>_<field>`; the prefix `x_packet_` is reserved.

**On which element.** A Relation with supertype `Work item`. **Where real links can exist**, the Relation's own typed link fields (`characters`, `locations` and the rest) carry the same elements as real links, so a tool that knows nothing of this profile still follows them: that is when the work item lives in the world its elements live in (a world's own room, a doctor filing into the world it checked). Across worlds (a link to an id the world does not hold is refused by the platform), and for the types a Relation has no link field for (Law, Map, Pin, Marker, Relation), `x_packet_elements` is the only carrier, and **a reader never lands a foreign id as a link**; `actor` is the one person the work is for, and `x_packet_for` the roles it is for (below); the description is the packet's own summary; the subtype is its state (`open`, `taken`, `done` or `standing`: rule 5). Before landing, the same keys sit in a bare JSON object with `type: "relation"`, `supertype: "Work item"`, `name` and `description`, and no `id` (the landing tool mints one); it may carry its state in `subtype` already, as both examples below do.

**The values.**

| Key | Meaning |
|---|---|
| `x_packet_elements` | A list of `{"type": "<type slug>", "id": "<element id>", "reason": "<one sentence>"}`. The type is carried so a reader needs no lookup to find the element's route or file; the id is the element's; the reason is why this element is in the packet, one sentence a person reads. Order is the producer's (a doctor's order of severity; a person's order of asking). An entry without all three keys is ignored by a reader, never repaired. |
| `x_packet_source` | `{"server": "<base URL, or null for a folder>", "world": "<world id>"}`: which world the ids belong to, in the shape of the folder format's provenance line (the folder format's `source`: its `server` and `world`), so a packet made from a folder on disk (`server: null`) and one made from an account world read the same. A packet read in a parlor world points at the SOURCE world, never at the parlor. |
| `x_packet_producer` | `{"tool": "<name>", "version": "<version>"}`, present only when a tool made the packet (the doctor, an agent's harness). A person's packet carries no producer: `created_by` already names them. `tool` is required whenever the key is present; `version` is optional: a writer that does not know the version leaves the key out, never invents one and never writes the word "unknown", and a reader takes a producer with no version as a producer whose version is not known. The `tool` and `version` of a world folder's `producer` (the folder format). |
| `x_packet_for` | Optional. A list of Title ids: the work item is for whoever holds one of them; `actor` stays the one person it is for. Both may be set. The ids are Titles of the world the work item sits in, as `actor` is a Character of that world; never of the world `x_packet_source` names. In a parlor world apart from its source, the people and their roles are the parlor's. It is not a link, so nothing follows it and no lens reaches a work item through it. |
| `x_packet_from` | Optional. One Character id, as a string: who asked for the work. The Character is one of the world the work item sits in, as `actor` is; never of the world `x_packet_source` names. Any Character of the world may ask, an AI's own Character included. Absent, the asker is not named (rule 8). It is not a link, as `x_packet_for` is not. |

**How a reader uses it.**
1. The elements are `x_packet_elements`, in that order; the Relation's typed links are the same set and a reader may use either. When the two disagree (a landing tool failed half way), `x_packet_elements` is the packet and the links are a view of it.
2. A reader resolves each `{type, id}` in the source world named by `x_packet_source`; an id it cannot find is reported as missing, never dropped and never guessed at. The source world is not the world the Relation sits in when the Relation lives in a parlor.
3. Who made it: `x_packet_producer` names the tool; absent, the maker is `created_by` (a person's membership, or a seat); `changed_via` says which door it came through. A reader shows "the doctor, 0.11.0" from the producer line and never infers a tool from the seat. A producer whose `tool` is missing, empty or not a string is ignored, never repaired (the packet reads as one no tool signed); a producer with no version is shown by its tool's name alone ("the doctor").
4. A packet's size is bounded by the extension cap (the platform's cap on extension keys; on onlyworlds.com, 64 KB per element for all its extension keys together, counted as compact JSON): about 400 to 700 entries. A producer with more splits the packet into several work items, named `<name> (1 of 3)`, `(2 of 3)`, each complete on its own; a reader sees several, never a truncated one. A writer that would exceed the cap refuses to write, never trims.
5. The state is the subtype, one of four words: `open`, `taken`, `done` and `standing` (rule 7). Every state is matched trimmed and without regard to case, as the room profile defines it, so ` Standing` and `OPEN` are `standing` and `open`. A subtype that is none of the four is no state, an empty or absent one included: the work item is shown, and is never open work. **Open work** is a work item whose state is `open` or `taken`: work that is not done; a `done` item, a `standing` one and one with no state are never open work. A reader offers to take a work item, or to set it done, only when it is open work. A reader changes the state by changing the subtype and nothing in the packet.
6. **For whom.** A work item is for a seat when `actor` is the seat's Character, or a Title in `x_packet_for` names that Character in its `holders`. Neither set: addressed to no one; a reader shows it apart ("not addressed to anyone"), never as for every role. An id in `x_packet_for` that is no Title of this world, or an empty string, is ignored and reported by a lint, never guessed at; an empty list reads as absent. A reader that does not know the key loses nothing: a packet without it is whole.
7. **A standing work item** (state `standing`) is never done: a standing order of work, a kept list. It is never open work: a reader of open work leaves it out, and counts it on none of the elements it names. A reader that shows it shows it as itself: its name, and beside each element the reason, in `x_packet_elements`' order (rule 1). Being no open work, it is never offered to take or to set done (rule 5), and no report sets it done (the report profile sets `done` only on open work, a work item that is still `open` or `taken`).
8. **Who asked.** The asker is the Character `x_packet_from` names. Absent or `null` (as the room profile's mark and the report profile's parent read a `null`), the asker is not named, with no lint, and a reader names none: never the maker (`created_by`, or the tool `x_packet_producer` names) and never `actor`. The key is read as written, as the address profile's "The same id" reads an id in an `x_` value: it names the element whose own `id` is written exactly so, and any other spelling is another value that names nothing. It is no asker, reported by a lint and never guessed at, when it is not one id (a value that is not a string, such as a list or a number, or a string that is empty once trimmed of White_Space, as the room profile trims; the trim decides only that, as in the report profile's rule 9) or when it names an element the reader holds that is no Character of this world (a Location, or a Character of the source world only). A value that names no element the reader holds (the id of one deleted, hidden from this reader or not served to it, or a spelling that no element's own `id` is written in) is an asker this reader cannot name: no asker is shown, with no lint, and none is guessed. "What am I waiting on" is a read: the open work whose `x_packet_from` is my Character, the Character the reader plays, so a person and an AI that play the same Character wait on the same items. A reader that does not know the key loses nothing.

**What a writer must do.**
- Write `x_packet_elements` and `x_packet_source` together, with `x_packet_elements` never empty, and `x_packet_producer` beside them only when a tool made the packet; a work item with no elements is a plain Relation, not a packet.
- Write the fourth, `x_packet_for`, only when the work is for a role, and never as an empty list: a writer leaves the key out instead of writing one.
- Write the fifth, `x_packet_from`, when the writer knows who asks, itself included when it asks (the Character it plays); a writer that does not know leaves the key out, never writes an empty string, and never puts a guess in it.
- Whoever writes the work item as an element writes its state in the subtype and never leaves it empty: `open` for work to be done, `standing` for work that is never done. A work item with no state is never open work (rule 5).
- Keep every entry's three keys; keep the source as the server and world it was made from; split past the cap.
- Keep it byte for byte when it is not yours to change, like every extension field. A re-key (a tool deliberately giving an element a new id, which may rewrite a value that is that old id, whole) never enters it: a packet is about the world named in `x_packet_source` with the ids that world had when the packet was made, and a copy of the world under fresh ids is a different world, where rule 2 reports the ids as missing.
- Reserve the prefix. A tool that lets people add their own fields reserves `x_packet_` and shows the five fields read-only, like `x_identity_`.

**What it is not.** A link field (a reader that ignores the profile still has the typed links), a record of what was done (the state is the subtype; the doing is in the elements' own changes), or a store of element text (a reason is one sentence about why, never a copy of the element). `x_packet_for` is a key and not the Relation's `titles` link because the typed links carry the packet's own elements (rule 1: the same set), so a Title in `titles` is one of the work's elements, never whom the work is for.

**The fixture.** `packet.fixture.json`, beside this page, holds the cases of rules 5, 7 and 8 every reader must agree on, read in the world its `world` names, with that world's Characters and the other elements of it the reader holds, and its `source_world` where a packet is about another world: each case is the work items as one reader is given them, in the order given, and a `want`. `state_cases`: each item's state (one of the four words, or `null` for no state), every item shown, and, for each element the items name, the open work that names it; and an item's elements in their order, compared only where the want carries them. `asker_cases`: each item's asker (a Character's id, or `null`), the lints, and for each Character what it is waiting on. In the want, `states`, `askers` and `elements` are keyed by the item's id, `open_work` by the element's id and `waiting_on` by the Character's; each but `elements` compares as a map, and `elements` is compared on the items the want names, each a list of element ids in order; `shown`, each list of work items in those maps and `lints`, each `{kind, item}` of the one kind `asker`, compare as sets. The cases cover: a standing item; `Standing ` with a capital and a trailing space; `open`, `taken` and `done` beside a standing item; a standing item with five elements; a standing item beside an open one, the want carrying only the standing item's elements; the subtype `blocked`; a work item with no subtype, a `null` one, an empty one and one of spaces alone; `open` followed by U+001F and `open` after U+FEFF, neither of which is White_Space; `ſTANDING`, whose long s folds to s; an asker; an item with no key, made by a person and one made by a tool, and one whose key is `null`; a key that names a Location, an empty string and a list; an asker the reader holds no element for; a Character's id in upper case and one with a space after it; an asker that is a number, one of White_Space alone and one of U+001F alone, which is no White_Space, and a word in no id's form; a Character whose own id is in upper case, named by that spelling and not by its lowercase one; two work items about another world, one asked by a Character of the world they sit in and one naming a Character of the source world only; what a Character is waiting on; a Narrative with supertype `Work item` and a Relation with supertype `Ally`, each with the subtype `open` and a packet's keys, given beside a work item, neither of which is a work item, so neither has a state, is shown or is open work; and a work item with no key whose maker in `created_by` is written as the id of a Character the reader holds, which names no asker. The rest of the page has no cases.
